# Git 提交规范

> 分类：conventions
> 适用范围：全局（所有模块、所有 Git 提交）
> 关键词：git, commit, 提交, Conventional Commits, message, push, 推送, 影响面, scope
> 最后更新：2026-10-03

## 背景

统一提交信息的结构与粒度，让每一次提交「改了什么、为什么改、影响哪里」都可追溯；同时防止在未获许可时误推远程，以及把无关改动混入提交。

## 内容

### 规则

1. **首行（标题）遵循 [Conventional Commits](https://www.conventionalcommits.org/)**：

   ```
   <type>(<scope>): <摘要>
   ```

   - `type` 取值：`feat`（新功能）、`fix`（缺陷修复）、`docs`（文档）、`style`（格式）、`refactor`（重构）、`perf`（性能）、`test`（测试）、`build`（构建/依赖）、`ci`（流水线）、`chore`（杂务）、`revert`（回滚）。
   - `scope` 可选，**优先使用业务目标或功能模块**（如 `3d-viewer`、`paint2d`、`offline-build`），不要用无意义的范围。
   - 摘要 = 本次改动内容的一句话总结，**使用中文**，不使用纯英文摘要；首行不加句号。

2. **正文必须写明（与首行之间空一行）**：
   - **目的**：这次改动是为了什么（解决什么问题 / 达成什么目标）。
   - **影响面**：影响哪些模块、文件、行为或产物；明确「无影响」的部分也可注明。
   - 如有验证，追加「验证」段：只写与本次主题直接相关、可追溯的验证方式与结果（命令 + 结果）；未验证项显式标注原因，不得写「全部通过」这类笼统表述。

3. **一次提交只覆盖一个清晰主题**：功能、配置、文档、依赖锁等不同主题分别提交；不跨模块捆绑无关改动。

4. **提交前冻结范围**：先查看 `git status`，只暂存本次任务相关文件（优先精确 `git add <文件>`）；出现来源不明或与本次目标无关的改动时，先列清单询问用户，不擅自打包提交。

5. **未明确要推送，则仅做本地提交**：只有用户明确说出「推送 / push / 提交并推送」时才执行 `git push`；否则提交完成即止，并告知用户当前提交停留在本地。

### 正例

```
feat(3d-viewer): 替换默认小熊为卡通3D造型

目的：默认模型为占位小熊，需替换为贴合美术风格的 Q 版卡通形象。
影响面：仅 src/three/viewer.js；新增 buildCartoonBear，移除失效 CDN GLB 加载路径。
验证：npm run build 成功（产物 708 kB）；浏览器内模型切换、涂色、喷雾正常，控制台无错误。
```

### 反例

- `update` / `修改` —— 无 `type`，不符合 Conventional Commits，且未总结改动。
- `fix bug` —— 未说明目的与影响面，无法追溯。
- 一次 commit 同时包含 3D 功能改动、知识库文档和依赖升级 —— 多主题混杂，应拆分。
- 用户只说「提交一下」就执行 `git push` —— 未获明确推送许可。

## 示例

最小合规结构：

```
<type>(<scope>): <改动内容摘要>

目的：<为什么做这次改动>
影响面：<影响的模块 / 文件 / 行为>
```
